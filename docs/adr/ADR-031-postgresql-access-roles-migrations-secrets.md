# ADR-031: PostgreSQL access: roles, migrations, secrets and the local database

- **Status:** Accepted (2026-10-01)
- **Date:** 2026-10-01
- **Review date:** 2027-04-01 (earlier if a trigger named in Consequences occurs)
- **Deciders:** owner (RedeArmy) with E1 plan approval

## Context
Slice S3 introduces the first persistent state: API clients, API keys and the audit log. Constitution sections 54 and 107 require backward-compatible migrations, SR-15 and SR-24 require separate database roles with an insert-only audit trail (INV-3), and ADR-018 requires that credentials only ever arrive through the `SecretStore` port. Deployment stays local-only (D1), so nothing here may depend on a cloud vendor.

## Decision
**Roles.** `deployments/postgres/roles.sql` creates four non-superuser login roles and revokes everything from PUBLIC: `fip_migrator` (owns schema objects, runs DDL, never used at runtime), `fip_app` (the API), `fip_admin` (operator tooling such as `cmd/keyctl`) and `fip_readonly` (analysts). `fip_admin` is an addition to the three roles named in SR-24: key issuing and revocation must not be possible from the runtime role, so a compromised API process cannot mint keys. Privileges are granted explicitly per table and per column in the migrations (fail-closed: a table without a grant is unreachable). The runtime role can read clients and keys and update only `api_keys.last_used_at`; no application role can `UPDATE`, `DELETE` or `TRUNCATE` `audit_events`; the read-only role cannot read `secret_hmac`. The script is idempotent, contains no passwords, and uses plain SQL so Docker init, CI and the Go test harness share it.

**Migrations.** golang-migrate, used as a library by `cmd/migrate`, with the SQL embedded in the binary (`migrations/`). They run as `fip_migrator`, never automatically when the API starts. `up` files may only add (a test rejects `DROP`, `TRUNCATE`, `DELETE`, renames and type changes, requires `REVOKE ... FROM PUBLIC` and a `GRANT` for every new table, and forbids update or delete grants on append-only tables); `down` files are for local development only, and `migrate down` is refused outside local and test environments and needs `-yes`.

**Secrets.** Database passwords are never configuration keys. `SecretStore` is a port; the only adapter today is `LocalStore` (environment variable `SECRET_<NAME>`, then a file under `SECRETS_DIR`, opened with `os.OpenRoot` so a name cannot escape the directory). It refuses to be constructed in production-like environments (SR-19), so production stays unusable until a managed adapter exists, which is intended while no vendor is chosen. Connection strings that contain a password exist only in memory and are stripped from error messages.

**Connections.** `pgxpool`, configured entirely from `Config` (the `PG*` environment variables and pgx defaults are overwritten so the process environment cannot redirect a connection). TLS is `verify-full` or `disable`; `require` without verification is deliberately not offered, there is no plaintext fallback, and production-like environments must use `verify-full`. Every session gets a statement timeout, a lock timeout and an idle-in-transaction timeout. The pool opens lazily: the API starts while PostgreSQL is still coming up and reports `not_ready` (a critical readiness check) until it answers, instead of crash-looping. Transactions retry serialization failures and deadlocks up to three times with jittered backoff; the callback must be safe to rerun. Database errors are classified into the platform error model, with the original error kept only as the logged cause.

**Local environment.** Docker Compose runs `postgres:17-alpine` pinned by digest. Every connection requires a password, including loopback inside the container (`--auth-host` and `--auth-local` set to `scram-sha-256`; the image default trusts localhost). Passwords are generated by `make local-secrets` into the git-ignored `./secrets` directory, mounted as Docker secrets and read by the same `LocalStore` the API uses. Integration tests use a separate throw-away database on `127.0.0.1:55432`, in memory and with trust authentication, which is acceptable only because it is bound to loopback and holds no real data; CI uses an equivalent job-scoped service container.

**Test harness.** `internal/platform/database/dbtest` creates an isolated database per test, applies the roles and, optionally, the migrations. Role passwords are derived by hashing, so no credential literals exist in the code. A privilege matrix test proves each role can do exactly what the design allows against a real server.

## Alternatives considered
- Auto-migrate when the API starts: mixed-version rollouts and a runtime role with DDL rights.
- A single database role: no separation between runtime, operator and schema authority; a compromised API could rewrite the audit log.
- An ORM or generated query layer: out of scope here; ADR-003 already chose SQL-first access.
- `sslmode=require`: encrypts without authenticating the server, which gives false assurance.
- Trust authentication for the development database: convenient, but it would hide credential and grant mistakes until deployment.

## Consequences
+ Privilege separation is enforced by the database and tested; a leaked runtime credential cannot change the schema, mint keys or alter the audit log.
+ The API tolerates a slow database start; operators see the truth through `/readyz`.
- A fourth role (`fip_admin`) and per-column grants increase the surface that migrations must keep correct; the privilege matrix test is the guard.
- Production-like environments cannot start until a managed `SecretStore` adapter is added with the cloud decision; staging and production configuration is validated but not yet usable.
- The throw-away test database uses trust authentication, so tests cannot detect a broken password setup; that path is verified by running the real Compose database (`make db-up`, `make migrate`).
- The pinned image digest needs periodic updates (Dependabot watches the Compose file).

## Rejected options
Superuser credentials in the API; storing the connection string in configuration; running migrations from the API process; granting `UPDATE` or `DELETE` on append-only tables to any application role.
